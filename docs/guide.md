# Подробное устройство проекта

Этот документ объясняет проект с точки зрения человека, который впервые его
открывает. Здесь описано, какие данные проходят через систему, какие вычисления
выполняются и почему отдельные части устроены именно так.

## Задача проекта

В симуляции есть четыре квадрокоптера. Один из них является ведущим, а три
остальных должны сохранять заданное положение относительно него. Ведущий
аппарат оснащён лазерным дальномером. Дальномер не сообщает готовые координаты
других аппаратов: он выдаёт облако точек, то есть множество точек, до которых
дошёл лазерный луч.

Проект должен решить несколько задач одновременно:

1. найти ведомые аппараты в облаке точек;
2. не перепутать их номера между соседними измерениями;
3. передать измерения через канал, в котором возможны задержки и потери;
4. вычислить команды движения для удержания расположения;
5. остановить перестроение, если данные стали недостоверными;
6. передать команды в PX4 и измерить результат.

Эталонное положение моделей Gazebo используется только для проверки. Контроллер
не читает его и принимает решения только по LiDAR, состоянию собственного
аппарата и ведущему состоянию.

## Общий ход работы

При запуске создаются четыре экземпляра PX4 и мир Gazebo. PX4 публикует
телеметрию через ROS 2. Ведущий LiDAR публикует облако точек. Облако проходит
через узел обработки, затем измерения передаются программным каналом связи.
Контроллер формы получает измерения и текущую форму, вычисляет команды скорости
для ведомых и отправляет их через мост автопилота в PX4.

Одновременно менеджер состояния проверяет время измерений. Если пакет пришёл
поздно, его собственное время измерения всё равно сохраняется: важен возраст
самого измерения, а не только время доставки.

## Пакеты и их ответственность

### `swarm_interfaces`

Это общий набор сообщений ROS 2. Он не управляет аппаратом, а задаёт формат
обмена между узлами:

- `RelativePose` — относительное положение ведомого, номер цели, время и
  достоверность измерения;
- `SwarmState` — положение, скорость, курс, режим, состояние связи и признак
  готовности аппарата;
- `SwarmCommand` — команда конкретному ведомому с целевой скоростью и временем
  её формирования;
- `FormationCommand` — название расположения, масштаб и длительность перехода.

Наличие времени и флага `valid` в сообщениях необходимо для того, чтобы нельзя
было принять старую или повреждённую информацию за новую.

### `lidar_tracker`: обработка облака точек

Трекер получает `PointCloud2` от LiDAR ведущего. Алгоритм состоит из следующих
этапов.

Сначала удаляются точки с нечисловыми координатами. Затем применяются простые
ограничения: дальность должна быть от 0,5 до 80 метров, а высота — в рабочем
слое, где находятся модели ведомых. Это убирает большую часть земли, неба и
далёких объектов.

Оставшиеся точки объединяются в связные группы. Для каждой точки ищутся соседи
в радиусе `cluster_tolerance` при помощи пространственного дерева KD. Если
сосед соединён с точкой, а через него — с другими точками, все они попадают в
один кластер. Это простая евклидова кластеризация: отдельные аппараты дают
отдельные группы точек. Слишком маленькие и слишком большие группы
отбрасываются, как и группы с чрезмерным размером.

Центр кластера вычисляется как среднее положение его точек. Для каждого из
трёх ведомых хранится последняя позиция и скорость. Новая позиция выбирается
по ближайшему прогнозу:

```text
прогноз = последняя позиция + последняя скорость × прошедшее время
```

Если ближайшая группа дальше `association_gate`, она не назначается цели. Если
две группы почти одинаково подходят или две цели претендуют на одну группу,
измерение помечается неоднозначным и не используется. Это консервативный выбор:
лучше временно потерять цель, чем незаметно поменять номера аппаратов.

После успешного сопоставления применяется экспоненциальное сглаживание:

```text
новая позиция = alpha × измерение + (1 - alpha) × прогноз
```

Скорость обновляется по разности положений. Если облако не приходит вовремя,
трекер публикует недействительное измерение. После длительной потери трек не
назначается новой цели автоматически. Для известной стартовой расстановки есть
сервис сброса, который повторно использует начальные позиции из YAML.

### `mesh_interface`: модель канала связи

Физическая радиосеть в проекте не моделируется. Вместо неё используется
программный канал с ограниченной очередью. При отправке сообщения он может:

- добавить постоянную задержку;
- добавить случайное отклонение задержки;
- отбросить сообщение с заданной вероятностью;
- отбросить сообщение при переполнении очереди.

Случайность задаётся начальным числом, поэтому один и тот же эксперимент можно
повторить. Исходная временная отметка сообщения не изменяется. Это позволяет
отличить старое измерение от свежего даже после задержки доставки.

Для проверки отказов есть ограниченная инъекция потери только сообщений
относительного положения. Она очищает очередь поз и на короткое время блокирует
новые позы, но не останавливает передачу состояний и команд.

### `swarm_manager`: проверка свежести

Менеджер не управляет двигателями. Он отвечает на вопрос, достаточно ли свежи
данные для продолжения работы:

- `FOLLOWING` — измерение допустимо и моложе короткого порога;
- `DEGRADED` — измерение ещё не потеряно, но уже старое;
- `HOLD` — измерение недействительно, пришло из будущего или старше длинного
  порога.

В текущей конфигурации короткий порог равен 0,3 секунды, длинный — 1 секунде.
Состояние публикуется как диагностика и используется контроллером как причина
для остановки перестроения.

### `formation_controller`: расположение и команды

Для каждой формы заданы три относительных вектора в системе координат ведущего:

- линия — три аппарата рядом по боковой оси;
- колонна — три аппарата один за другим;
- клин — два аппарата сзади по сторонам и один по центру.

Векторы умножаются на общий масштаб. До начала перехода проверяется минимальная
дистанция между всеми четырьмя аппаратами, включая ведущий.

При смене формы контроллер перебирает все шесть вариантов назначения трёх
ведомых на новые места. Для каждого варианта он проверяет прямой путь между
старым и новым расположением. Минимальная дистанция на таком пути вычисляется
аналитически, а не только в нескольких дискретных точках. Выбирается допустимый
вариант с наименьшей суммарной длиной перемещений. Если безопасного варианта
нет, запрос отклоняется.

Переход выполняется функцией сглаженного шага:

```text
s(u) = u² × (3 - 2u)
```

где `u` меняется от нуля до единицы за заданное время. В начале и конце такого
перехода скорость изменения места равна нулю.

Для каждой цели используется регулятор по относительной ошибке. Если `r` —
измеренное положение ведомого, а `o` — нужное положение, основная поправка
имеет вид `Kp × (o - r)`. К ней добавляются скорость ведущего, скорость самого
слота при перестроении и поправка на вращение ведущего:

```text
скорость = скорость ведущего
         + поправка на ошибку
         + скорость изменения слота
         + угловая скорость ведущего × вектор слота
```

Последний член нужен, когда ведущий поворачивается: место ведомого движется по
дуге даже при постоянной форме.

После регулятора работает ограничитель. Он использует два последовательных
сглаживающих звена и ограничивает норму скорости, ускорения и рывка при
фиксированном периоде 0,05 секунды. При недостоверных данных целевая скорость
становится нулевой, то есть аппарат получает команду торможения.

Дополнительно контроллер следит за наблюдаемым минимальным расстоянием. При
опасном сближении он отключает управление формой. Это инженерная защита команды
и не является математическим доказательством отсутствия столкновения в реальном
аппарате.

### `leader_interface` и `mission_planner`

Ведущий может получать ручную скорость или следовать по пути. Планировщик строит
путь алгоритмом A* по сетке занятости. Сетка расширяется на радиус всей формы
и запас безопасности, поэтому препятствие учитывается не только для ведущего,
но и для ведомых.

Алгоритм A* хранит для каждой клетки стоимость уже пройденного пути `g` и
оценку оставшегося расстояния `h`. В очередь выбирается клетка с минимальным
`g + h`. Разрешены восемь направлений движения, но диагональный шаг через угол
двух препятствий запрещён. Если цель недостижима или карта устарела, путь
отклоняется.

### `autopilot_bridge`: связь с PX4

В ROS 2 используется система координат ENU: X на восток, Y на север, Z вверх.
PX4 использует NED: X на север, Y на восток, Z вниз. Мост явно меняет оси и
знак высоты. Кватернионы и угловые скорости также переводятся из PX4 FRD в
ROS FLU.

Мост читает только телеметрию PX4 своего аппарата, состояние роя и команды
контроллера. Команда принимается, только если она действительна, относится к
правильной системе координат, не старше тайм-аута и не пришла из будущего.
Потеря команды приводит к нулевой целевой скорости.

Для PX4 публикуется режим управления скоростью и наборы заданий с ограниченной
частотой. Перед переходом в Offboard сначала некоторое время отправляются
служебные сообщения, затем проверяется подтверждение PX4. Вооружение, взлёт,
посадка и переходы режима выполняются сервисами, а завершение проверяется по
телеметрии и подтверждениям, а не только по ответу сервиса.

### `evaluation`: проверка результата

Модуль оценки отдельно получает эталонные позы моделей из Gazebo. Он не
публикует их в управляющие темы. Для каждого времени измерения он вычисляет:

- ошибку положения ведомых относительно ожидаемых мест;
- ошибку всей формации;
- минимальную дистанцию между аппаратами;
- долю пропущенных или устаревших измерений;
- время и состояние сценария.

Результаты сохраняются в CSV и JSON, после чего строятся графики. Эталонная
поза включает поправку между центром модели и центром видимой части, потому что
LiDAR видит поверхность, а не математический центр аппарата.

## Время и безопасность

Все узлы симуляции используют единые часы Gazebo. В сообщениях хранятся два
разных понятия: время, когда измерение было сделано, и время, когда оно было
получено. Старая доставка не делает старое измерение новым.

При возврате часов назад очереди и временные водяные знаки очищаются. Будущие
сообщения не принимаются. При остановке LiDAR перестроение не продолжается по
последней известной позе: контроллер тормозит и переходит в удержание.

## Что важно понимать о текущей реализации

Это воспроизводимый симуляционный прототип, а не готовая система для реального
полёта. Номера целей первоначально привязываются к известным стартовым местам.
Центр кластера LiDAR — это центр видимой поверхности, а не полноценная оценка
позы аппарата с ориентацией. Ограничители скорости учитывают команды проекта,
но не моделируют все задержки и физику конкретного полётного контроллера.

Ground truth, абсолютные координаты ведомых и данные карты не используются как
замена LiDAR в контуре удержания формации.

## Проверки

Основные автоматические тесты находятся рядом с пакетами в каталогах `test`.
После сборки из корня проекта их можно запустить так:

```bash
python3 -m pytest src -q
```

Отдельные smoke-скрипты проверяют синтетическую цепочку, четыре экземпляра PX4,
обработку LiDAR и мост команд. Их результаты нужно трактовать как проверки
конкретного этапа, а не как доказательство полной безопасности системы.
