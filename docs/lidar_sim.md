# Настоящий LiDAR в Gazebo

`worlds/swarm_lidar.sdf` сохраняет имя мира `swarm`, физику и стартовые
координаты baseline `swarm.sdf`. Лидер использует `swarm_x500_leader`,
три ведомых — `swarm_x500_target`. Обе модели расширяют штатный PX4 `x500`
через `include merge=true`; исходники PX4 не меняются.

Сенсор `gpu_lidar` находится относительно `base_link` лидера на `(0, 0, 1.9)` м.
Это виртуальное высокое крепление для симуляционного эксперимента: реалистичная
мачта, её масса и аэродинамика не моделируются. Такое упрощение нужно для
исследования видимости колонны; оно не означает готовый корпус реального БПЛА.
Оси совпадают с FLU корпуса: X вперёд, Y влево, Z вверх, yaw=0. Полный
горизонтальный обзор 360°, вертикальный от −30° до +30°, 1024×64 луча,
10 Гц, диапазон 0.15–80 м. Рендеринг выполняет Sensors с Ogre2; даже запуск
без GUI требует работоспособного графического контекста для GPU LiDAR.

Тема Gazebo `/uav_0/lidar/scan/points` имеет тип `gz.msgs.PointCloudPacked`;
`config/lidar_bridge.yaml` направляет её только GZ_TO_ROS в
`/uav_0/lidar/points`, `sensor_msgs/msg/PointCloud2`. Значение `frame_id`
задаётся сенсором как `uav_0/lidar_link`. Clock идёт из `/world/swarm/clock`
в ROS `/clock`; все участвующие узлы должны использовать `use_sim_time`.
Параметры файла описывают контракт: получение облака и точное имя frame
необходимо подтвердить интеграционным запуском на конкретной машине.

Ведомый несёт пассивную сферическую мишень радиуса 0.25 м, её центр находится
на `(0, 0, 0.45)` м относительно своего `base_link`. Мишень видима сенсору
через visual и имеет collision; масса добавленного link составляет 0.01 кг.
Это явное упрощение симуляционного эксперимента. При горизонтальных корпусах
и равной высоте аппаратов относительный Z центров мишеней в frame сенсора
равен −1.45 м. Контроллер учитывает отдельные extrinsics сенсора (0,0,1.9)
и мишени (0,0,0.45), без подмены LiDAR-измерений ground truth.

Трекер измеряет центроид видимой поверхности сферы, а не её геометрический
центр и не `base_link` ведомого. В FLU лидера переход из frame LiDAR в
`base_link` добавляет `(0, 0, 1.9)` м. Чтобы оценить позицию корпуса из
центра мишени, затем нужно вычесть повёрнутый в frame лидера offset мишени.
Без оценки ориентации ведомого это допущение корректно лишь при близких
roll/pitch. Даже при горизонтальном полёте остаётся смещение от видимой
поверхности, которое следует измерять отдельно через evaluation.

Исторический фильтр Z `[-0.30,0.30]` больше не подходит. Фильтр, начальные
seeds трекера, статический TF и поправки контроллера должны быть согласованы
с Z=−1.45. Их изменение и проверка выполняются отдельным этапом интеграции.

## Аналитическая проверка окклюзии

Предполагаются горизонтальные корпуса на одной высоте, сферы r=0.25 м и колонна
с расстояниями 4s, 8s, 12s позади лидера, scale s∈[0.8,1.3]. Перестановка
трёх ID даёт те же точки, поэтому результат одинаков для всех 3! назначений.
Разность высоты сенсора и центров сфер a=1.45 м. Расстояние от центра средней
сферы до луча в центр дальней:

`d = (a/3) / sqrt(1 + (a/(12s))²)`.

Минимум d=0.477913 м при s=0.8; запас над радиусом — 0.227913 м.
Угловые силуэты средней и дальней сфер также не пересекаются: их зазор
около 0.518° при s=0.8 и 0.348° при s=1.3. Для разделения силуэтов во всём
диапазоне достаточно a≥1.265544 м; выбранная высота даёт дополнительный запас.
Верхняя граница силуэта ближней сферы при s=0.8 — 28.457°, внутри ±30°.

Дискретная проверка ray-sphere intersection на 1001 значении scale=0.8..1.3
с 1024×64 лучами дала минимум 72/20/8 попаданий в ближнюю/среднюю/дальнюю
мишени. Учтена конкуренция сфер по ближайшему пересечению; вертикальный шаг
около 0.952°. При 32 вертикальных лучах было лишь 32/8/2 попадания в худших
точках диапазона; поэтому вертикальная плотность увеличена вдвое. Это расчёт
идеальной геометрии, а не подтверждение трекера: наклон, колебания высоты,
корпус, noise, дискретизация GPU и поверхность мишени меняют число точек и
смещают центроид. Нужны реальные облака во всех формациях, scale и переходах.

Проверка синтаксиса и разрешения включаемых моделей из корня проекта:

```bash
export GZ_SIM_RESOURCE_PATH="$PWD/src/swarm_lidar/models:/home/smag/PX4-Autopilot/Tools/simulation/gz/models"
export SDF_PATH="$GZ_SIM_RESOURCE_PATH"
gz sdf -k src/swarm_lidar/worlds/swarm_lidar.sdf
gz sdf -k src/swarm_lidar/models/swarm_x500_leader/model.sdf
gz sdf -k src/swarm_lidar/models/swarm_x500_target/model.sdf
```

`gz sdf -k` проверяет описание, но не работу Ogre2, поток ROS и точность
трекера. До живого теста эти результаты не считаются подтверждёнными.
Для `gz sdf` нужен именно `SDF_PATH`: в отличие от `gz sim`, валидатор
не разрешает `model://` только по `GZ_SIM_RESOURCE_PATH`. Мир успешно прошёл
эту проверку; предупреждения о расширении `gz_frame_id` ожидаемы для SDF 1.9.

## Исторический проверенный запуск: сенсор Z=0.45 м

```bash
source /opt/ros/jazzy/setup.bash
source ~/px4_ros_ws/install/setup.bash
source install/setup.bash
ROS_DOMAIN_ID=72 ros2 launch swarm_lidar swarm_demo.launch.py gui:=false lidar:=true
```

Во втором терминале с тем же окружением:

```bash
ROS_DOMAIN_ID=72 python3 scripts/smoke_lidar.py
```

Чекпоинт 2026-10-20 с прежними Z=0.45 м и FOV ±20°: получено настоящее
облако 1024×32, frame совпадает,
три цели дали минимум 10 валидных измерений. Измерены координаты
(-3.888,-3.894,0), (-3.834,0,0), (-3.888,3.894,0) м.
Отклонение от nominal slots около 0.16 м связано в том числе с поверхностью
мишени; это не RMSE относительно ground truth. Интеграционный полётный тест
отдельно подтвердил четыре взлёта, Offboard, движение на восток, торможение
после остановки команд и четыре посадки. Контур формации ещё не подключён.

Этот исторический результат не подтверждает новую высоту 1.9 м, FOV ±30°
и плотность 1024×64. После синхронизации TF/трекера/контроллера необходимы
повторный smoke LiDAR, проверка column при scale=0.8..1.3, всех переходов
и полётных отклонений.
