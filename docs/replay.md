# Повторная обработка записанного облака

`scripts/replay_tracker.py` запускает новый трекер и пассивную оценку из
записи MCAP. Gazebo, PX4 и управление аппаратами для этого не нужны.
Скрипт передаёт трекеру исходные точки, а эталонные положения — только
оценке. Сохранённые результаты прежнего трекера и команды аппаратов
не воспроизводятся.

После сборки подключите окружение ROS 2 и `install/setup.bash`. Нужны пакеты
`lidar_tracker`, `evaluation`, поддержка MCAP в rosbag2 и Python-пакет PyYAML.
Запись должна содержать непустые `/uav_0/lidar/points` и
`/evaluation/ground_truth`. Исходное облако сохраняется при запуске
сценария с `--record-cloud`.

Выберите начало участка, когда все аппараты уже взлетели и стоят в известных
начальных местах из параметра `initial_positions`. Сброс старого трекера
через сервис в запись не попадает. Если воспроизвести последовательный
взлёт с земли, трекер может потерять соответствие номеров аппаратам ещё до
начала эксперимента. Начало посреди перестроения также не подходит для
инициализации прежними начальными местами. Скрипт не выводит номера целей
из эталонных положений и не восстанавливает их таким способом.

```bash
python3 scripts/replay_tracker.py log/ЗАПИСЬ/bag \
  --output log/НОВАЯ_ОЦЕНКА \
  --start 49 --end 120 --domain 83 --rate 0.5 --reliable-cloud \
  --params-file log/параметры_трекера.yaml \
  --evaluation-params-file log/параметры_оценки.yaml
```

`49` и `120` здесь — пример границ в секундах времени записи, а не готовые
границы для любой записи. Начало bag берётся из `metadata.yaml`; смещение
для rosbag2 вычисляется автоматически. Время `/clock` создаёт проигрыватель.
Темп `0.5` даёт трекеру больше реального времени на обработку, сохраняя
исходные отметки измерений. Ускорение выше `1` запрещено.

`--reliable-cloud` включает надёжную доставку только при повторном анализе:
проигрыватель публикует облака с Reliable QoS, а отдельный процесс создаёт
тот же `LidarTracker` с надёжной подпиской. Алгоритм, отметки времени и
проверка свежести сохраняются. Подписка в обычной симуляции остаётся
BestEffort. Режим доставки записывается в `result.json`, настройки
проигрывателя — в `playback_qos.yaml`. Без этого флага действует прежний
режим подписки; крупные облака могут дополнительно теряться при локальном
повторе даже при замедлении. Поэтому режимы нельзя смешивать при оценке
надёжности передачи в исходном полёте.

Домен должен быть свободным. Домен `72` и текущий `ROS_DOMAIN_ID` запрещены;
перед запуском выполняется проверка видимых узлов выбранного домена.
Проверка не резервирует домен: не запускайте другие приложения в нём во
время обработки. Скрипт завершает только собственные группы процессов.
Существующий выходной каталог не перезаписывается.

Параметры должны соответствовать записанной модели. В ранних записях над
аппаратами были сферические мишени: для них использовались начальная
высота `-1.45`, фильтр высоты до `-0.65`, а в оценке `marker_z: 0.45`.
Обновлённая модель без мишеней использует другие параметры. Нельзя оценивать
старое облако как новую геометрию. Снимки прежних файлов можно извлечь из
соответствующего коммита:

```bash
git show b183f54:src/lidar_tracker/config/tracker.yaml > log/старый_трекер.yaml
git show b183f54:src/evaluation/config/evaluation.yaml > log/старая_оценка.yaml
```

Для повторения прежней обработки укажите также `ground_filter: false`
в разделе `lidar_tracker.ros__parameters` исторического файла: в новой версии
удаление плоскости земли включено по умолчанию. Снимок YAML старого коммита
сам по себе не возвращает прежнюю реализацию программы. Сравнение разных
версий алгоритма нужно обозначать явно.

При отсутствии явных путей используются текущие файлы параметров из
исходного дерева. Их копии сохраняются в результате, как и точная команда
проигрывателя. Вход и выход трекера принудительно назначаются на
`/uav_0/lidar/points` и `/swarm/relative_poses`; время обоих узлов — время ROS.

В выходном каталоге находятся:

- `relative_poses.jsonl` — новые результаты трекера с номерами целей,
  отметками измерений, координатами, достоверностью и признаком пригодности;
- `metrics/samples.csv` и `metrics/summary.json` — ошибки относительно
  записанного эталона и доли пропусков;
- `tracker.yaml` и `evaluation.yaml` — использованные файлы параметров;
- `tracker.log`, `evaluation.log`, `play.log` — журналы процессов;
- `result.json` — границы, темп, домен, число новых сообщений и результат
  завершения. Успех требует новых пригодных измерений и сопоставленной с
  эталоном локализации всех трёх целей.

При надёжной доставке создаётся `tracker_input_diagnostics.json`. Входные
облака и уникальные отметки считаются внутри единственной подписки трекера,
без второй сетевой копии. Отдельно считаются отбрасывания из-за неверного
кадра координат, старого, будущего или немонотонного времени. Для непригодных
результатов указываются причины: таймер устаревания, отсутствие подходящих
кластеров, несопоставленные цели или ошибка чтения облака. Эти счётчики
относятся к результатам отдельных целей, поэтому один срез может дать три
непригодных результата. Их нельзя складывать с числом отвергнутых облаков.

Записанные задания формации и статусы воспроизводятся только для разбиения
метрик. Ошибка формации при таком повторе характеризует прежний полёт;
изменение трекера меняет оценку локализации и доступности измерений, но
не перемещает аппараты в уже записанном эксперименте.

Повтор не гарантирует побитового совпадения: исходная запись могла потерять
сообщения, а доставка и таймеры ROS зависят от нагрузки. Сравнивайте ошибку
вместе с долей пропусков и журналами. Геометрия, частота и пропуски сырого
облака остаются такими, какими они были при записи.

Проверка на исторической записи S1 от 20 октября 2026 года, участок
49–75 с, показала: при темпе `0.5` с надёжной доставкой приняты все 157
записанных облаков, получены 471 пригодный результат для трёх целей.
Среднеквадратическая ошибка локализации — 0.152 м, пропусков эталона нет.
Таймер свежести дополнительно выдал 51 непригодный результат; доля
временных срезов с устаревшим измерением — 8.05%. В сырой записи есть
разрывы до 0.8 с и задержка момента записи облака относительно его
отметки около 0.104 с. Поэтому эта доля отличается от 1.15% у сохранённых
поз исходного полёта. Порог свежести при повторе не изменялся.
Без надёжной доставки в том же окне дополнительно потерялись 22 из
157 облаков; замедление до `0.25` само по себе потери не устранило.
Это проверка повторной обработки, а не доказательство полной эквивалентности
доставки сообщений исходному эксперименту.
