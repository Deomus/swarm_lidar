# Исполнители сценариев

Взлёт, установление формы и миссия ограничены временем симуляции `/clock`.
Дополнительно действует предел реального ожидания — вчетверо больше
бюджета манёвра, минимум 10 с. Поэтому замедленная запись видео не расходует
бюджет полёта как реальное время, а остановившиеся часы не приводят к
бесконечному ожиданию. Проверки свежести состояний остаются прежними.

Перед вооружением запрашивается штатный HOLD каждого PX4: после посадки
может оставаться AUTO_LAND, в котором повторный arm не проходит проверку.
Предполётные проверки остаются включёнными. Для сравнимых экспериментов
рекомендуется новый запуск мира перед каждым сценарием.

Для раздельного анализа времён перестроений и ручных входов:

```bash
python3 scripts/analyze_scenario.py log/s2_ДАТА_ВРЕМЯ \
  --output log/s2_ДАТА_ВРЕМЯ/analysis.json
```

Скрипт согласует журнал событий с CSV по времени симуляции. Для ручного
входа метрики вычисляются отдельно для каждого заданного уровня скорости;
окно включает разгон, повороты и торможение, поэтому его нельзя считать
измерением установившегося движения с постоянной скоростью.

Для записи обмена сообщениями добавьте `--record-bag`. Параметр
`--record-cloud` включает также исходное облако LiDAR и подразумевает запись
остальных тем. В каталоге сценария появятся `bag/` в формате MCAP и
`rosbag.log`. В запись входят состояния, команды, относительные позы,
целевые места, диагностика, маршрут, эталонные координаты и часы.

```bash
ROS_DOMAIN_ID=72 python3 scripts/run_scenario.py s1 --record-cloud
ros2 bag info log/s1_ДАТА_ВРЕМЯ/bag
```

Поле `bag_recorded` подтверждает штатное завершение записи и наличие
метаданных; оно не доказывает отсутствия потерь. Проверяйте счётчики
сообщений и предупреждения о потерях в журнале. Облако значительно увеличивает
объём и нагрузку. Воспроизведение содержит команды управления, поэтому для
анализа используйте отдельный ROS_DOMAIN_ID, в котором не запущены PX4-мосты.

Посадка отправляется всем четырём аппаратам, затем запросы повторяются
для оставшихся вооружёнными. Устаревшее сохранённое `armed=false` не считается
подтверждением: нужны свежие состояния всей группы. Ошибка выполнения
сценария и ошибка посадки записываются отдельно как `run_error` и
`landing_error` в `result.json`, чтобы сбой посадки не скрывал исходную причину.

В S3 завершение проверяется по свежему статусу `COMPLETE`, после чего
подтверждаются удержание линии и остановка ведущего в пределах 0.5 м от
запрошенной точки со скоростью менее 0.15 м/с в течение секунды. Отказы
`WAYPOINT_TIMEOUT`, `STATE_STALE`, `CLOCK_RESET`, `PATH_REVOKED` завершают
ожидание с конкретной причиной. Позиция ведущего берётся из его PX4,
эталон Gazebo в принятии решений сценария не используется.

После завершения каждого перестроения S1 записывает ещё 10 секунд удержания.
Это отдельное окно наблюдения за остаточной ошибкой; порог первичного
достижения места остаётся 0.6 м в течение секунды.

S2 после ручного сопровождения включает потерю LiDAR-поз в mesh на 0.7 с.
Проверяются `DATA_HOLD` и свежие недействительные нулевые команды трём
ведомым, затем возврат к удержанию линии. Реакция физических скоростей
оценивается отдельно: нулевая команда сама по себе не доказывает мгновенную
остановку аппарата. Последовательность S2 пока является автоматизированной
проверкой ручного входа, а не записью управления оператором.

Исполнитель предназначен только для текущей симуляции. Он отправляет
настоящие ROS-запросы и ждёт подтверждения состояния; принудительный arm
не используется. Каждый запуск сохраняет отдельный каталог log/ с журналом
событий, CSV и summary evaluation. Исходный ground truth в управление не идёт.

Запуск симулятора в первом терминале:

```bash
source /opt/ros/jazzy/setup.bash
source ~/px4_ros_ws/install/setup.bash
source install/setup.bash
ROS_DOMAIN_ID=72 ros2 launch swarm_lidar swarm_demo.launch.py gui:=false lidar:=true
```

Во втором терминале с тем же окружением:

```bash
ROS_DOMAIN_ID=72 python3 scripts/run_scenario.py s1
```

S1 выполняет последовательный взлёт лидера и ведомых, bootstrap LiDAR в
известных слотах, Offboard, line, изменение высоты, scale1→1.15→1,
line→column→wedge→line, HOLD и посадку. Критерий установления — свежий
статус FOLLOWING и три ошибки регулятора менее 0.6 м на протяжении секунды.
Это критерий по LiDAR, а не ошибка относительно GT.

`s2` проверяет ручной вход программной последовательностью TwistStamped на
трёх скоростях. Это воспроизводимый тест интерфейса, а не видеодоказательство
работы человека с клавиатурой. `s3` передаёт карту и цель в A*, затем включает
исполнение пути лидером. Полётные проверки обоих сценариев с посадкой
выполнены; актуальные результаты и ограничения приведены в [отчёте](report.md).

При исключении исполнитель пытается перевести контуры в HOLD и посадить
аппараты. Итог passed требует успешного сценария и подтверждённой посадки.
Старый статус или устаревшие состояния не должны давать положительный итог.

## Исторический чекпоинт 2026-10-20

Полётная последовательность S1 прошла. После переключений получены ошибки
по LiDAR: column [0.228,0.062,0.238], wedge [0.459,0.224,0.299],
финальная line [0.037,0.047,0.485] м. Все аппараты сели и разоружились.

Проблема первого recorder: преобразование Gazebo Pose_V через общий TF bridge
потеряло имена и время поз; GT-метрики отсутствуют и не считаются измеренными.
Потребуется повтор с исправленным evaluation reader. Этот прогон также не
является полной приёмкой проекта: нет трёх видео и проверки S2/S3.
