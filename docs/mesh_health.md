# Канал mesh и контроль свежести

Для воспроизводимой проверки потери измерений предусмотрен Trigger
`/mesh/drop_relative_poses`. Он очищает очередь относительных поз и блокирует
новые позы на `drop_duration=0.7` секунды времени симуляции. Состояния и команды
продолжают передаваться; временные отметки не переписываются. После окончания
окна новые измерения проходят автоматически. При откате часов окно и очередь
сбрасываются. Сам сенсор и его трекер продолжают работать: проверяется отказ
доставки измерений, а не физическое перекрытие LiDAR.

Параметр `drop_target_id` (по умолчанию 0) выбирает цель: 0 — все позы,
1..3 — только поза этого ведомого, без очистки очереди остальных. Так
проверяется выбывание одного ведомого из строя (DEGRADED).

`mesh_interface` — программный интерфейс, без моделирования радиофизики.
Он передаёт сообщения без изменения полей и timestamp:

| Вход | Выход | Тип |
|---|---|---|
| `/swarm/relative_poses` | `/mesh/relative_poses` | `RelativePose` |
| `/swarm/states` | `/mesh/states` | `SwarmState` |
| `/swarm/commands` | `/mesh/commands` | `SwarmCommand` |

QoS: reliable/volatile, depth из YAML. На каждую тему своя ограниченная
очередь. Задержка и равномерный jitter задаются в секундах, loss в [0,1].
Переполнение отбрасывает новый пакет. Seed фиксирует воспроизводимость; каналы поз, состояний и команд
используют `seed`, `seed+1` и `seed+2`, чтобы их потери не совпадали.
Jitter может менять порядок доставки. При возврате ROS-времени назад очередь
очищается. Частота доставки ограничена `period` (по умолчанию 100 Гц).

`swarm_manager` принимает `/mesh/states` и `/mesh/relative_poses`, публикует
`/swarm/health` (`diagnostic_msgs/DiagnosticArray`, reliable, volatile) на
10 Гц. Имена статусов — `uav_0..uav_3`. Проверяются timestamp измерения и
телеметрии, valid и наличие обоих потоков для ведомых. Лидеру LiDAR-поза
самого себя не требуется. Приём старого пакета не обновляет last seen.

## Режим группы (ТЗ §8)

`swarm_manager` также работает супервизором: из свежих `SwarmState`
(armed, `nav_state` PX4, `health` моста), статуса строя и статуса ведущего
он вычисляет один режим и публикует `/swarm/mode` (`std_msgs/String`, JSON
`mode`, `reason`, `time`) на 10 Гц; тот же режим — статус `swarm` в
`/swarm/health`. Каждый переход пишется в журнал с причиной и временем.
Супервизор только наблюдает и команд не выдаёт; реакции выполняют узлы.

| Режим | Условие (по приоритету) |
| --- | --- |
| FAILSAFE | эскалация моста (`FAILSAFE_HOLD/LAND`) или строй COLLISION_STOP / INVALID_GEOMETRY |
| DEGRADED | нет свежей телеметрии аппарата, нет статуса строя, строй DATA_HOLD / DEGRADED |
| DISARMED | все аппараты разоружены |
| LAND | вооружённый аппарат в AUTO_LAND (`nav_state` 18) |
| TAKEOFF | не все вооружены или не все в Offboard |
| FORMING | контур строя не включён или ошибка места ≥ `forming_error` (0,6 м) |
| FORMATION_CHANGE | идёт перестроение |
| MISSION | ведущий в MISSION |
| FOLLOWING | ведущий в ручном режиме, ведомые сопровождают |
| HOLD | строй установлен, ведущий удерживается |

Режим записывается в rosbag сценариев и показывается в панели рядом с
состоянием полёта; причина — во всплывающей подсказке.

Свежие данные дают FOLLOWING, краткий stale — DEGRADED, длительный stale,
invalid, отсутствие данных или timestamp из будущего — HOLD. Здесь FOLLOWING
означает готовность данных, а не подтверждение полёта. Выход пока не является
командой автопилоту. Переходы логируются с причиной и ROS timestamp.

Настройки находятся в `config/mesh.yaml` и `config/manager.yaml` соответствующих
пакетов. Параметры считываются при старте. Все узлы используют одни часы.

Запуск после сборки и source install/setup.bash:

```bash
ros2 run mesh_interface mesh_node
ros2 run swarm_manager manager_node
ros2 run swarm_manager health_check --ros-args -p expected_uavs:=4
```

Каждая команда запускается в отдельном терминале. Без источников состояний
и измерений проверка health должна завершиться ошибкой.

Воспроизводимый тест с синтетическими облаками и телеметрией (без PX4):

```bash
ROS_DOMAIN_ID=71 python3 scripts/smoke_pipeline.py
```

Он проверяет три LiDAR-цели, четыре health status, передачу через mesh и HOLD
после остановки облаков. Это проверка ROS-цепочки, не приёмка SITL/S1/S2/S3.
