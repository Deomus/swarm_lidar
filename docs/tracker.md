# LiDAR-трекер

Вход: `/uav_0/lidar/points`, `sensor_msgs/PointCloud2`, QoS sensor data
(best effort, volatile, depth 1). Для крупных облаков сохраняется последнее
ожидающее измерение, чтобы обработка не накапливала очередь старых кадров.
Глубина задаётся `cloud_qos_depth`. Обязательны поля float x/y/z и frame
`uav_0/lidar_link`. Выход: `/swarm/relative_poses`, `RelativePose`, reliable,
volatile, depth из YAML. Публикуется отдельное сообщение на каждого ведомого.
Единицы: метры, секунды. Timestamp сохраняется из облака.

Координаты описывают центр видимого кластера в frame LiDAR. Ориентация цели
не измеряется: quaternion identity — заглушка, использовать yaw цели нельзя.
Трекер выделяет точки самого корпуса штатного X500, без дополнительных шаров
или кубов. Центроид видимых деталей лишь приближённо совпадает с центром
аппарата: это смещение измеряет независимый модуль оценки.

Алгоритм: конечные точки → диапазон → удаление плоскости земли RANSAC
(включается параметром) → высота → связные компоненты радиусного
графа через KD-tree → ограничения размера и протяжённости → центроид →
сопоставление по предсказанию постоянной скорости → EMA. Confidence —
эвристика компактности кластера, не вероятность и не covariance.

Начальные позиции в `config/tracker.yaml` — явно заданные места старта
ведомых относительно лидера. Это допущение начальной идентификации, не
подписка на ground truth. Сортировка кластеров не задаёт ID. При конкуренции
двух целей за кластер или близких кандидатах измерение помечается invalid.
После потери длиннее `reacquire_timeout` трек не предсказывается и не
участвует в обычном сопоставлении. Он возвращается автоматически только у
своего последнего положения: ближайший кластер должен быть в пределах
`association_gate`, не занят живым треком, отделён от второго кандидата
`ambiguity_margin` и не нужен другому потерянному треку. Скорость трека
обнуляется, событие записывается в журнал узла. Иначе цель остаётся
invalid. Произвольная повторная идентификация, например после перемещения
аппаратов во время потери, этим не решается: для неё по-прежнему нужен
`/lidar_tracker/reset` при известной расстановке.

Старые, будущие, повторные облака и неверный frame отклоняются. Если поток
прекратился, таймер продолжает публиковать invalid с исходным timestamp.
В Gazebo все узлы должны использовать `use_sim_time:=true` и один `/clock`.

Параметры хранятся в YAML пакета: диапазон, размер кластера, порог
компактности, расстояние сопоставления, EMA, timeout, темы и очередь.
Параметры считываются при старте; для изменения требуется перезапуск узла.

Проверка: `python3 -m pytest src/lidar_tracker/test -q`. Покрыты шум,
нечисловые точки, разделение кластеров, пропажа, сохранение ID, неоднозначные
цели, повторный захват после длительной потери только у последнего
положения и отказ при неоднозначности. Реальное облако Gazebo ещё
не проверено; без него этап интеграции LiDAR не считается завершённым.

Обновление: неподвижный настоящий поток проверен в docs/lidar_sim.md.
Перед включением строя после последовательного взлёта есть сервис Trigger
`/lidar_tracker/reset`: он повторно привязывает треки к initial_positions из
YAML. Вызывать его можно только при известных стартовых слотах. Это не
восстановление произвольной потерянной цели в движении.
